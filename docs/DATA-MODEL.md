# FLORAL — MongoDB Models (authoritative field specs)

Exact from ERD Chapter 3. **Read this before touching any schema, model, or migration.** CLAUDE.md carries only a pointer to this file to keep per-session context small; this doc is the authority for field-level details. Cross-cutting rules (soft delete, encryption, auth) stay in CLAUDE.md.

**SCHOOL** — school_id, school_name, school_type, principal_name, street_address, barangay, city, created_at, updated_at, isArchived, archivedAt, archivedBy

**USER** — user_id, **school_ids (ARRAY of School FKs — ERD DEVIATION, Sprint 100; replaced the ERD's single `school_id`. EMPTY MEANS ALL SCHOOLS, which is how system_admin and bho_staff have always behaved. One dentist and one aide rotate across all three schools and other roles may cover several, none of which a single FK could express. `DENTIST_ROTATION` does not cover this — it is a weekly schedule, not an access grant. ⚠ Chapter 3's ERD figure still shows `school_id` and must be updated.)**, role (system_admin/dentist/dental_aide/school_admin/bho_staff), full_name, email (added Sprint 7 — login identifier, unique, not in original ERD), password_hash (added ahead of Sprint 7, not in original ERD, `select: false` so it never returns in queries by default), is_enrolled (BOOLEAN), last_login, **twofa_enabled (BOOLEAN default false), otp_hash (`select: false`), otp_expires (DATE), reset_token_hash (`select: false`), reset_token_expires (DATE) — none in the original ERD; they back the 2FA enrolment and password-reset flows. The two `_hash` fields are `select: false` so they never return from a query by default, the same protection as `password_hash`**, created_at, updated_at, isArchived, archivedAt, archivedBy

**DENTIST** — dentist_id, school_id (FK), user_id (FK), last_name, first_name, license_number (VARCHAR 50), created_at, updated_at, isArchived, archivedAt, archivedBy

**DENTAL_AIDE** — dental_aide_id, school_id (FK), user_id (FK), dentist_id (FK), last_name, first_name, contact_number (VARCHAR 20), created_at, updated_at, isArchived, archivedAt, archivedBy

**STUDENT** — student_id, school_id (FK), last_name (VARCHAR 60, required — added Sprint 35, not in original ERD), first_name (VARCHAR 60, required — added Sprint 35), middle_name (VARCHAR 60, optional — added Sprint 35), full_name (VARCHAR 150), birthday (DATE), sex (VARCHAR 10, required), address (VARCHAR 200 — the student's HOME address, not the school), contact_number (VARCHAR 15), grade_level (required unless `is_not_student`), section (required unless `is_not_student`), **guardian_name, guardian_contact, philhealth_number, philhealth_status (enum None/Principal/Dependent, default None), is_4ps (BOOLEAN default false), fourps_id, consent_status (enum pending/complete, default pending) — none in the original ERD; they come from the DOH IPTR paper form, which prints all of them. `guardian_name`, `guardian_contact`, `philhealth_number` and `fourps_id` are ENCRYPTED (see the encryption list in CLAUDE.md)**, created_at, **is_demo (BOOLEAN, default false — added Sprint 117, not in original ERD)**, **is_not_student (BOOLEAN, default false — added 2026-09-25, not in original ERD)**, isArchived, archivedAt, archivedBy
- **`is_demo` (Sprint 117, 2026-09-04) — ⚠ DEVIATES FROM THE CHAPTER 3 ERD.** Marks a record created by a seeder rather than by a real encoding session. **Only the seeders set it true**; everything a person creates — the Add Student form, the CSV/xlsx import, OCR — takes the `false` default and is therefore real by construction (verified by test, not by intention). `purgeDemoData.ts` deletes on this flag alone, so a hand-encoded record is unreachable by the purge whatever it is named. **Why it exists:** before this, the only thing separating demo from real data was a hardcoded list of 26 names in `demoStudents.ts`. That list had already drifted once (Sprint 45 added eight pupils the purge's copy never learned about), the first real hand-encoded record landed 2026-09-04, and Phase 3 adds 50 more. Existing rows were backfilled by `npm run backfill:is-demo` (dry-run by default); the purge **refuses to run** if any record looks like demo data by name but lacks the flag, rather than falling back to name matching. Not encrypted — it is not PII and the purge queries on it.
- **`is_not_student` (2026-09-25) — ⚠ DEVIATES FROM THE CHAPTER 3 ERD.** Marks a person recorded through the Add Student form who isn't actually enrolled at the school (e.g. a sibling or community member treated at a Bayanihan mission). Checking "Not a Student" on that form clears and disables Grade and Section only -- Sex still applies to a non-enrolled person and stays required either way. The schema's `required` on `grade_level`/`section` is a conditional validator (`!this.is_not_student`) rather than a plain `true`, so these two are the only fields allowed to be absent, and only for this case; `sex` keeps a plain `required: true`. The STUDENT_IPTR record created alongside still gets opened, with `grade_level`/`section` sent as `null` (already optional there per Sprint 57a) rather than empty strings. Defaults `false`: every existing and normally-added pupil is unaffected. Not encrypted — it is a status flag, not PII.
- **Name split (Sprint 35, 2026-08-25).** The original ERD gave STUDENT a single `full_name`, but the DOH IPTR paper form has separate name boxes and every list/report is read surname-first, which one string cannot support. This follows the ERD's own convention — **DENTAL_AIDE already splits `last_name`/`first_name`** — so it is a consistent extension, not a new pattern. **`full_name` is retained but is now DERIVED**: a `pre('save')` hook rebuilds it from the parts, so it stays valid for every existing reader while the parts remain the single source of truth. The hook is registered BEFORE the encryption plugin (mongoose runs pre-save hooks in registration order); reversing that order would write a plaintext `full_name` over the encrypted one.
- Existing records were migrated by `server/scripts/splitStudentNames.ts` (dry-run by default, idempotent, handles suffixes and surname particles, flags ambiguous names rather than guessing).
- All four name fields are encrypted, so the **Sprint 26 random-IV rule applies: plaintext equality queries on them never match** — fetch and filter in JS.

**STUDENT_IPTR** — iptr_id, student_id (FK), school_year (VARCHAR 20), **grade_level, section (added Sprint 57a, not in original ERD — STUDENT holds ONE current grade/section, so without these every PAST year silently reported the pupil's grade TODAY, and a DOH report scoped to an old year was wrong. These are the placement AS AT that school year; STUDENT keeps its own as the CURRENT values), height_cm, weight_kg (NUMBER, added Sprint 68, not in original ERD — per-year measurements the IPTR form carries, with BMI derived rather than stored)**, created_at, isArchived, archivedAt, archivedBy
- ⚠ **Uniqueness: one IPTR per (student_id, school_year)**, enforced by `uniqueBy` on the route and an index. This is why Promote / Assign must PUT an existing year record rather than POST a second one (Sprint 102), and why Bulk Transfer edits the current year in place (Sprint 123).

**MEDICAL_HISTORY** — medical_id, iptr_id (FK), allergies (TEXT), diabetes_mellitus (BOOLEAN), hypertension (BOOLEAN), cardiovascular_disease (BOOLEAN), thyroid_disorders (BOOLEAN), hepatitis_disorders (BOOLEAN), malignancy (BOOLEAN), previous_hospitalization (BOOLEAN), previous_surgical (BOOLEAN), blood_transfusion (BOOLEAN), tattoo (BOOLEAN), others (TEXT), created_at
- **Yes/no fields are plain BOOLEAN, default false.** They are the History tab's tick-box chips; on DOH Form 1 a ticked chip prints under Oo and an unticked one under Hindi (user decision, 2026-09-24). A year with no MEDICAL_HISTORY saved prints the questions blank, and Q12/Q13 print blank for male pupils.
- **⚠ ERD DEVIATION (2026-09-24, user-approved):** `blood_disorders` (BOOLEAN, the IPTR's Blood Disorders row, which had nowhere to be stored); DOH Form 1's Filipino questions that no ERD field answers: `liver_disease` (Q3), `anemia` (Q4), `anesthesia_allergy` (Q7), `previous_extraction` (Q8), `extraction_bleeding` (Q9), `chest_tightness` (Q10), `asthma` (Q11), `menstruation` (Q12, female only), `pregnant` (Q13, female only), `current_medication` (Q15), `epilepsy` (Q16), `high_blood_pressure` (Q5, its own chip; Form 1 prints Oo when it OR `hypertension` is ticked), all BOOLEAN default false; and the forms' "Please specify" / "Ano?" details `hepatitis_type`, `malignancy_details`, `blood_transfusion_date` ("Month & Year"), `last_admission` (IPTR "Medical (Last Admission & Cause)"), `medication_details` (Form 1 Q15), `last_extraction_date` (Form 1 Q8, optional), `surgical_details` (IPTR "Surgical (Post-Operative)"; `previous_surgical` is set true exactly when this is filled), all TEXT, **ENCRYPTED**. Q3 and Q4 are deliberately NOT answered from `hepatitis_disorders` / `blood_disorders`: "sakit sa atay" is broader than hepatitis and "kulang sa dugo" is one kind of blood disorder. ⚠ Chapter 3's ERD figure must be updated.

**DIETARY_SOCIAL_HABITS** — dietary_id, iptr_id (FK), sugar_beverages (BOOLEAN), alcohol_drinker (BOOLEAN), tobacco_user (BOOLEAN), betel_nut_chewer (BOOLEAN), body_piercing (BOOLEAN), nail_biting (BOOLEAN), thumb_sucking (BOOLEAN), created_at

**ORAL_HEALTH_CONDITION** — oral_id, iptr_id (FK), oral_hygiene (VARCHAR 50), gingivitis (BOOLEAN), periodontal_disease (BOOLEAN), debris (BOOLEAN), calculus (BOOLEAN), abnormal_growth (BOOLEAN), cleft_lip_palate (BOOLEAN), others (TEXT), created_at
- **The IPTR summary's "Orally Fit Child" row is AUTOMATIC, not a stored field (2026-09-25, superseding a same-day `orally_fit_child` field that was added then reverted).** Computed client-side in DentalChart.tsx (`isOrallyFitChild`) as: none of the oral conditions above present AND no tooth carries a treatment code. **⚠ Unrelated to Dashboard/Reports' separate "Orally Fit" indicator** (`oralStatus === 'Orally Fit'`, itself `risk === "Low"` from RISK_STRATIFICATION) — same name, different definition, kept deliberately apart; see the comment on that derivation in Dashboard.tsx.

**DENTAL_CHART** — chart_id, iptr_id (FK), dentist_id (FK), date_charted (DATE), isArchived, archivedAt, archivedBy
- **`preventive_id` (FK → PREVENTIVE_CARE_RECORD, NULLABLE — Sprint 149, ⚠ ERD DEVIATION, superseded 2026-09-25 same day — see below).** Originally: the ONE RPC visit this charting was done at, under a 1 chart = 1 visit model.
- **(2026-09-25) Visit 1 and Visit 2 now share ONE dental chart instead of each getting their own.** A single chart can no longer point at two visits through one FK, so `preventive_id` is not written by the current save flow at all — Visit 1/2's services are looked up directly by `(iptr_id, visit_number)` on PREVENTIVE_CARE_RECORD (`preventivesByVisitNumber` in `useDentalChartData.ts`), independent of any chart. `preventive_id` stays on the schema as a legacy/read-only field for charts created under the old model; new charts leave it null. Which visit a given TOOTH_RECORD's current treatment belongs to is now tracked per-tooth instead (see `visit_number` on TOOTH_RECORD below). Ticking a service in Treatments Given still creates the visit itself when it doesn't exist yet (Visit 1 or 2, whichever this school year is missing) — same "only when a real service was ticked" guard as before, since an invented visit still shifts the DOH return's 1st/2nd application count.
- **⚠ SEVERAL CHARTINGS PER SCHOOL YEAR ARE STILL NORMAL** for reasons unrelated to Visit 1/2 (e.g. charting done outside the RPC visit flow entirely) — measured 2026-09-05, 22 of 26 IPTRs on dev have two or more. Code that reads `charts[0]` is wrong; Sprint 148 fixed the one screen that did.


**TOOTH_RECORD** — tooth_record_id, chart_id (FK), tooth_number (INT), condition (VARCHAR 100), treatment_code (VARCHAR 50)
- **`visit_number` (INT, enum 1/2, default null — added 2026-09-25, ⚠ ERD DEVIATION).** Which RPC visit this tooth's CURRENT condition/treatment was recorded at. One tooth still holds one current value, not a history — a second treatment on the same tooth at Visit 2 overwrites Visit 1's entry for that tooth, same as any other re-charting. This is what the odontogram's "(V1)"/"(V2)" tag under a tooth's treatment code reads, and what the chart tab's Treatment Summary splits its Visit 1 / Visit 2 columns on. Null for every tooth charted before this field existed and for charting done outside the visit flow — not every tooth belongs to a visit. "Visit 1" everywhere in the UI treats null the same as an explicit 1 (a catch-all default), so nothing charted before this feature existed silently drops out of the summary.

**TREATMENT** — treatment_id, iptr_id (FK), dentist_id (FK), diagnosis (TEXT), treatment_done (TEXT), remarks (TEXT), date (DATE), created_at, isArchived, archivedAt, archivedBy

**PREVENTIVE_CARE_RECORD** — preventive_id, iptr_id (FK), visit_date (DATE), visit_number (1 or 2), **facility_based (BOOLEAN, default null — added Sprint 81, not in original ERD; the FHSIS report splits every count into facility-based and school-based sub-rows (a/b), which cannot be derived from anything else. `null` means not recorded, and is deliberately distinct from `false`)**, created_at, isArchived, archivedAt, archivedBy
- **Services performed AT the visit (Sprint 147) — ⚠ ERD DEVIATION:** `oral_screening`, `oral_prophylaxis`, `fluoride_varnish`, `oral_hygiene_instruction` (BOOLEAN, **default null**) and `caries_risk` (ENUM `Low` | `Moderate` | `High`, default null). **`consultation` (BOOLEAN, default null — added 2026-09-25, per the user, same field pattern as the other four)** is tracked here too, but ⚠ deliberately NOT printed on the Target Client List — the paper form has no Consultation column, and CLAUDE.md's "copy official forms exactly" rule means a field absent from the form stays absent from it, not silently added.
- **Why:** until Sprint 147 this model had four fields and recorded that a pupil was SEEN, never what was DONE — while CLAUDE.md's module 5 defines an RPC visit as exactly these services and page 2 of the Target Client List prints them as per-visit tick columns. The TCL therefore answered *"has this pupil EVER had fluoride varnish?"* from the dental chart where the form asks *"was it done at THIS visit?"*.
- **⚠ DEFAULT null, NEVER false** — the same rule `facility_based` follows. Every visit recorded before Sprint 147 has no answer, and `false` would claim on a filed form that a service was withheld. The TCL renders null as BLANK and only an explicit `true` as a tick.
- **⚠ `caries_risk` stores the FORM's word:** the form prints **Moderate** where `RISK_STRATIFICATION.risk_level` says **Medium**. On the form, the form wins.


**RISK_STRATIFICATION** — risk_id, preventive_id (FK), risk_level (VARCHAR 50: High/Medium/Low), recommendation (TEXT), dmf_score (FLOAT), dmf_index (VARCHAR 10: DMF or dmf), validated_by_dentist (BOOLEAN), validated_at (DATETIME)

**APPOINTMENT** — appointment_id, student_id (FK), dentist_id (FK), appointment_datetime (DATETIME), status (VARCHAR 50), appointment_type (added Sprint 11, not in original ERD), requires_followup (BOOLEAN, added Sprint 11), parental_supervision_required (BOOLEAN, added Sprint 11), isArchived, archivedAt, archivedBy. One Appointment record per student — a UI "session" (whole class section scheduled at once) is multiple Appointment records sharing date/time/dentist/type, grouped client-side. **notes (VARCHAR 500, optional, default '' — ERD DEVIATION, added Sprint 109): a remark on THIS pupil's slot ("bring guardian", "reschedule, absent"). Distinct from DAY_NOTE, which is about the date itself — the user confirmed the two are different things. No migration needed; it defaults empty.**

**DAY_NOTE** (NEW — ERD DEVIATION, added Sprint 108) — day_note_id, date (DATETIME, midnight local — one calendar square = one date), **school_id (FK, NULLABLE — ⚠ null means EVERY school, which is the barangay-wide holiday case and the reason the field is not required)**, note (VARCHAR 500), created_by (FK USER), created_at, updated_at, isArchived, archivedAt, archivedBy. A note written against a DATE rather than a patient ("no clinic, holiday", "compressor down"). ⚠ Because `school_id` may be null it needs the `school_id_or_global` rule in `schoolScope.ts` — a plain `{school_id: {$in: […]}}` excludes null and would hide every barangay-wide note from scoped users. Not overloaded onto DENTIST_ROTATION.notes, which is scoped to school + dentist + WEEK. ⚠ Chapter 3's ERD figure must be updated.

**REFERRAL** (NEW — ERD DEVIATION, added Sprint 127) — referral_id, iptr_id (FK — parented on the IPTR like TREATMENT, NOT on STUDENT, so a referral belongs to a school year and inherits that year’s grade), dentist_id (FK, NULLABLE — an aide may record one and no DENTIST row is linked to an aide account), **referral_type (ENUM, REQUIRED: `primary_care` | `higher_level` | `oral_cancer_screening` | `surgical` | `private_facility`)**, date_issued (DATE), facility_name (VARCHAR 120), reason (TEXT, ENCRYPTED), notes (TEXT, ENCRYPTED), status (ENUM `pending` | `completed` | `no-show`, default `pending`), follow_up_date (DATE, nullable), created_by (FK), created_at, updated_at, isArchived, archivedAt, archivedBy
- **The enum IS the DOH Oral Health Program Report’s printed row list**, not a taxonomy of ours — each of the form’s five referral rows is a count of one value, which is what lets those rows be filled without a judgement call at report time. ⚠ `oral_cancer_screening` / `surgical` / `private_facility` print INDENTED under “Total no. of patients referred to Higher Level of Care”, so that total counts `higher_level` PLUS those three; recording a surgical referral as `higher_level` as well would double-count the patient.
- **The form counts PATIENTS, not slips:** two referrals of the same kind for one pupil in one school year is one patient on that row (`useDohReportData` de-duplicates with a Set per IPTR).
- **`reason` and `notes` are encrypted; `facility_name` deliberately is NOT** — same class as `TREATMENT.diagnosis` for the first two, while a facility is an institution rather than patient PII and stays queryable. Sprint 26’s random-IV rule therefore applies to `reason`.
- **ISSUE-ONLY by design (2026-09-05).** `status` and `follow_up_date` exist but nothing drives a follow-up workflow: whether the clinic closes a referral out is unconfirmed with the dentist. Ask before building on them.

**DENTIST_ROTATION** (NEW — not in original ERD, added Sprint 11) — rotation_id, school_id (FK), dentist_id (FK), week_start (DATE), week_end (DATE), notes (TEXT), isArchived, archivedAt, archivedBy

**AUDIT_TRAIL** — audit_id, user_id (FK), action (VARCHAR 100), timestamp (DATETIME), affected_record_id, affected_model (VARCHAR 50)
